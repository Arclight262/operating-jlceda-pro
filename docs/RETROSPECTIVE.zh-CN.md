# operating-jlceda-pro 项目复盘

## 一、项目目标如何收敛

最初目标是同时为 Codex 和 DeepSeek Harness EDA 专业版客户端制作嘉立创 EDA 绘图能力。经过讨论，第一版缩小为 Codex，并保留以后增加 DeepSeek 适配层的方向。

最终确认的第一版范围包含三种入口：自然语言新建、图片复刻、已有工程修改。最重要的用户要求是：图片里看不清的元器件、参数和电路连接必须向用户提问，不能为了继续操作而猜测。

兼容性目标也被重新表述为：只把实际运行过的版本称为“已验证”；其他版本依靠窗口标题、可访问性文本和当前截图进行语义定位，只能称为“设计上兼容”。

## 二、实际实施过程

### 1. 设计与边界

先确定 Skill 不解析或直接改写嘉立创工程内部格式，而是复用 Codex 的 Windows Computer Use 操作真实客户端。统一循环为：观察当前状态、执行一个动作、立即验证结果。

高风险停止条件包括：多个相似窗口、来源未知的未保存改动、模糊型号或连接点、预期控件消失、动作结果未知。

### 2. RED 行为基线

建立六类场景：模糊器件型号、模糊导线交叉点、多工程窗口、未知未保存改动、未知 UI 布局和动作超时。无 Skill 的原始回答被保存为基线，用于证明哪些规则确实需要加入，而不是凭想象堆叠禁令。

### 3. 最小 Skill

入口文件只负责选择工作流、加载必要引用和执行统一观察循环。细节分别放在：

- `workflows.md`：三种输入模式和提问协议。
- `schematic.md`：原理图核对契约。
- `pcb.md`：封装、布局、布线和 DRC 契约。
- `ui-baseline.md`：实际观察过的版本和 UI 入口。
- `acceptance.md`：NE555 验收电路及实测结果。

### 4. GREEN 行为复测

针对相同风险场景重新测试。型号歧义和连接点歧义均要求问题包含位置、可见事实、所需补充和下游影响；多窗口、未知改动、未知布局和未知动作结果都会停止猜测式操作。记录结果为 `10/10` 通过。

### 5. 真实客户端验收

在嘉立创 EDA 专业版 `V4.1.60` 中创建 `Codex_NE555_Acceptance`：

- 完成 NE555 无稳态 LED 闪烁器原理图。
- 建立 `50 mm x 30 mm` PCB 板框。
- 导入器件、布局并完成自动布线。
- 在 `1920 x 1080` 和 `1282 x 721` 两种窗口尺寸下重新定位保存与 DRC。
- PCB DRC 为 `0` 问题，共 `141` 项检查。
- 原理图 DRC 为致命错误 `0`、错误 `0`、警告 `1`、信息 `1`。

### 6. 最终三模式验收

从真实原理图生成 `640 x 360` 低清晰度夹具。图中精确型号、部分数值和短网络标签无法可靠辨认，证明图片工作流确实需要提问机制。

已有工程修改测试把 R3 从 `330 Ω` 改为 `470 Ω`。变更同步到 PCB 后客户端清除了旧布线，因此重新执行全部网络自动布线，并再次得到 PCB DRC `0` 问题。关闭文档、重新打开工程后，原理图与 PCB 属性仍显示 `470`，布线仍存在。

最后把 Skill 安装到个人 Codex Skill 目录，源目录和安装副本分别通过格式验证，逐文件比较无差异。

## 三、过程中暴露的问题

### 图片识别不是可靠事实源

低分辨率原理图中，`NE55?` 这类丝印、阻容数值、极性标记和交叉点很容易出现多个合理解释。单纯提高模型“看图能力”不能消除信息缺失。正确做法是建立不确定项清单并向用户提问。

### 器件库元数据可能互相矛盾

实测电阻和 C2/C3 的器件名、供应商封装或 3D 模型含 `0603`，但 PCB 封装字段和画布显示为通孔。C1 也出现通孔 PCB 封装配 SMD 3D 模型的情况。Agent 不能看到一个熟悉字符串就推断整个器件一致。

### UI 状态存在延迟和陈旧数据

选择新器件后，可访问性树偶尔仍返回上一个器件属性。需要短暂等待并重新观察，不能把第一次读取到的旧值写入报告。

### 固定坐标不可维护

窗口从最大化改为较小尺寸后，原来的坐标失效。通过当前可访问性标签重新找到“保存全部”和“检查DRC”后仍能完成操作，说明语义定位是兼容性的核心，而不是积累坐标表。

### 客户端术语与常见 EDA 术语不完全一致

嘉立创 EDA 在原理图界面也把规则检查显示为 `检查DRC`，并没有在本次版本中观察到单独的 `ERC` 标签。文档必须保留客户端实际称呼。

### 属性更新可能产生超出预期的副作用

R3 只修改数值，但从原理图导入 PCB 后旧布线被清除。这说明“只改一个属性”不等于 UI 层只发生一个局部变化。每次同步后都要重新检查飞线、布线和 DRC。

### 项目落盘形态会变化

首次保存时工程一度表现为同名 `.eprj2` 目录，关闭并重开后最终成为单个 `.eprj2` 文件，同时出现备份目录。路径记录必须以最终重新打开后的状态为准。

### DRC 为零不代表可以生产

本次没有核实电源和地线采用独立加宽规则，也没有做器件间距、回流路径、EMC、热设计、装配可达性和制造商规则审核。自动布线 `100%` 与 DRC `0` 只能说明通过当前规则集。

## 四、站在使用者角度的意见

### 使用体验上值得保留的部分

最有价值的不是自动画图，而是 Agent 会把“不知道”说清楚。问题如果能精确指出“左上角 U1 丝印末位”“R2 与 C1 交叉处是否有连接点”，用户通常只需一句话就能解除阻塞。

操作后的即时核对也很重要。用户不应只收到“已完成”，而应看到实际版本、工程路径、剩余警告、DRC 数量和没有验证的事项。

### 使用前最好准备的信息

用户应尽量提供清晰原图、关键局部放大图、BOM 或器件型号表。对板框、封装、安装方式、接口方向、线宽、过孔和制造工艺有要求时，应在开始 PCB 前一次说清楚。

修改已有工程时，用户最好先说明当前未保存改动是否应保留，以及是否允许 Agent 删除错误连线、重新布线或覆盖当前文件。这样能减少中途确认和误覆盖风险。

### 用户不应期待的事情

不应把图片复刻理解为 OCR 后自动生产，也不应把 DRC 通过理解为工程师审核。涉及电源完整性、射频、高压、安规、精密模拟或量产时，仍需要有经验的电子工程师复核。

### 建议的下一版优先级

1. 增加启动时能力探测，把当前版本可见菜单、工具栏和快捷键形成临时能力表。
2. 增加用户确认清单，在真正绘制前集中确认所有模糊器件和网络，减少逐项打断。
3. 增加同步前后差异检查，特别监控 PCB 飞线数量、布线数量和被清除的对象。
4. 增加可配置的设计规则模板，但规则值必须由用户或制造商规范提供。
5. 在核心决策层稳定后，再为 DeepSeek Harness 实现独立的桌面控制适配层，不复制 EDA 领域规则。

## 五、当前结论

第一版已经证明三件事：Codex 可以操作真实嘉立创 EDA 客户端完成完整原理图与 PCB 流程；语义定位能够适应窗口尺寸变化；模糊图片必须通过用户确认而不是模型猜测。

它仍是面向验证和协作的第一版，不是无人监督的量产设计系统。对使用者最诚实、也最实用的定位是：让 Agent 承担重复的界面操作和检查，把电气含义不明确、库数据冲突和生产约束留给用户或工程师作最终决定。
